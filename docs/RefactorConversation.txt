One thing I would not do

I would not try to make the DAG itself the editable source for code.

But the software ecosystem expects:

to operate on a filesystem.

I wouldn't fight that.

Instead I'd embrace it:

The filesystem is the execution projection of a richer collaborative model.

That preserves compatibility with every existing tool while letting the DAG represent much more than "Git history with metadata."

The question I'd spend time answering next

I think there's one architectural object that keeps emerging from this discussion:

What exactly is a Projection?

Right now, it sounds like a projection mostly means "the planner selected these files."

I suspect it could become the central abstraction of Studio:

It defines what knowledge is visible.
It defines what code is materialized.
It defines which branch or experiment is active.
It defines which decisions and constraints apply.
It defines which execution environment should be used.
It is reproducible and versioned.

If you can define that object well, then everything else—workers, experiments, A/B testing, reviews, merges, builds—becomes different ways of creating, transforming, comparing, and materializing projections.

That feels much more aligned with the platform you've been describing than trying to make the DAG replace the filesystem or trying to eliminate the execution plumbing.
